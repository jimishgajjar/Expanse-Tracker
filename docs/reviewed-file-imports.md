# Reviewed transaction files

From **Settings → Open CSV / Excel import**, read the columns, confirm the mapping and currency, then preview the rows. Staging stores a pending batch in the active workspace; it does not change balances. A matching header layout reuses the last mapping in that workspace. Check it each time.

Each row needs an explicit decision: ignore it, match one existing transaction, or add a transaction. When dates, account, type and amount repeat, adding another entry is explicitly labelled as a separate purchase. Notes need not match. The same existing ledger entry cannot be matched twice in one batch. Incorrect or unsupported rows can only be ignored; the other reviewed rows can still be approved together. Unsaved choices are local to the screen until approval. Re-preview a pending file to change its mapping or refresh matches.

**Inputs.** Comma-separated UTF-8 CSV (including quoted fields and multiline notes), or XLSX with a Transactions sheet or one worksheet. Limits: 512 KB, 300 data rows, 40 columns and 500 characters per cell. Excel formula/object cells are flagged, not evaluated. Date formats are ISO, day/month/year or month/day/year. Amounts must be plain decimals: a Type column supplies income/expense; without one, positive means income and negative means expense. Workspace currency is confirmed explicitly; mapped foreign/blank currency values are errors. Accounts must already exist and be active. A named category must exist for the corresponding type. No references are automatically created. This imports income and expenses only: leave transfers out of signed bank files. Tags, currency conversion, bank-specific debit/credit pairs and restoring a multi-sheet backup are outside this workflow.

**Receipts.** A workspace-scoped SHA-256 of the original file bytes identifies a batch even after renaming a file. A completed batch is immutable through the importer: repeated submissions, lost responses, and deleted resulting transactions do not cause recreation. A changed/re-encoded file is a new batch; potential matches still need review. Different files are not proof that two similar entries are the same purchase. The importer serializes approvals per workspace and checks preview version, role, currency, account/category and ledger candidates again before writing. Any failed row rolls back the batch. Each added transaction, its creation history and the batch receipt commit together. Match and Ignore never update existing transactions. The Excel export includes batch identities, source row numbers, decisions and linked ledger IDs; encrypted backups include the new table.

**Local preview.** Run `npm run dev:preview`, open Settings, and try [the synthetic CSV](examples/statement-import-demo.csv) against the demo Cash and Bank accounts. It contains two similar expenses, a refund and an invalid date.

**Rollout.** `REVIEWED_FILE_IMPORTS=1` is enabled in the isolated preview; it disables the old immediate-import action. Off by default, the app retains its previous importer. Migration 0013 adds a new table and two invoker-rights SQL functions, without backfilling or rewriting financial tables. Before enabling in production: rehearse the new functions, rollback and concurrent approval on disposable hosted PostgreSQL, create and restore-verify a fresh encrypted production backup, and verify financial records before and after the additive rollout. Do not replace a live ledger with an old snapshot. This milestone does not connect a real bank.

**Local verification, 3 November 2026.** The optimized preview build passed with TypeScript checks, and the full suite passed 172 tests. The browser smoke test used a separate seeded demo database: the four-row fixture warned about identical purchases, blocked the invalid date, required all four decisions, and returned a receipt for two added and two ignored rows. Integration tests covered matching, rollback, stale previews, repeat uploads after deletion, workspace isolation, real XLSX parsing and scoped export receipts. Encrypted backups of synthetic schemas 0011, 0012 and 0013 were decrypted and restored with the original financial rows intact. This is local evidence, not verification of a live Neon deployment.
