## Accounting contracts exercised here

- Manual entry amounts are positive, exact decimal values with at most two decimal places and the existing `numeric(14,2)` limit. Income/expense carries direction. Excess precision is rejected rather than silently rounded.
- A valid calendar date is required, including leap-year checks. Stored dates are date-only values; no timezone conversion is applied.
- Income/expense, account, category, tags and current actor must belong to the active workspace. Categories must match the transaction type. Archived accounts cannot receive new manual postings.
- Transfers remain separate movements and cancel in household totals. This change does not claim complete refund, credit-card, foreign-currency, split-allocation, or recurring/manual duplicate accounting.
- Fixture: bank opens at 100.00, an old expense is 12.34, and a transfer out is 20.00. A new 6.50 expense must leave 61.16; old rows and the 20.00 transfer stay unchanged.

## Creation receipt and retry contract

`createWithHistory` normalizes the input and hashes the payload. The existing history primary key stores a hash of workspace + actor + request identity, prefixed with `create:`. The creation event has an empty `before` snapshot and an `after._creation` marker with schema version, payload hash and manual source. No new table or migration is needed.

A single parameterized SQL statement checks/locks membership and references, claims the receipt using a unique constraint, inserts the transaction, and attaches tags. Failure in any write rolls back the statement. Concurrent conflict handling reads the committed receipt in a fresh statement, avoiding the PostgreSQL statement-snapshot conflict visibility issue. The chosen SQL design still requires actual Neon HTTP concurrency validation before release.

- Repeating the same key and normalized payload returns the original transaction ID with `replayed: true`.
- A different payload under a committed key is rejected; it does not update the original or create another entry.
- Identical genuine purchases with different keys remain separate transactions.
- A retry after deletion is rejected and does not recreate the entry. A retry after editing never reverts the edit.
- A retry rechecks current workspace access, including viewer/member changes. It can acknowledge a previous save even if the account has since been archived.
- Legacy clients can omit the key: their transaction/tags/audit still commit atomically, but a separate retry cannot be identified. Old mobile builds need updating to obtain retry protection.
- Web and native forms keep the key after a network error, synchronously guard duplicate submissions, and clear it after an acknowledged save. Native reload failures retain the key. Keys are uniqueness markers, not credentials.
- Keys are currently in component memory, not durable offline storage. Reloading/unmounting a form before resolving an uncertain save loses that identity. Check Activity before re-entering; persistent encrypted drafts are M9 work.
- The history table must not be pruned or cascade-deleted with transactions without a replacement durable receipt store. Workspace deletion remains the existing explicit workspace-level lifecycle.

The history UI identifies Created versus Edited events and shows original values. Existing Excel exports and encrypted backups already include the history table. No historical creation events are reconstructed. Scheduled/file-import creation events are not added by this slice.

The new benchmark creates an in-memory PGlite database, migrates it in isolation, and generates 1k/10k/100k synthetic entries. It checks page size, exact income/expense totals, and workspace isolation while timing all activity, filtered search, and last-page retrieval. It never loads `.env`, connects to the application database, or sends telemetry. JSON receipts are saved under ignored `.codex/benchmarks/`.

The baseline identified per-row JSON/tag hydration before pagination in `activity-query.ts`. This slice moves display hydration after the materialized selected page while keeping filtering, full-filter totals and pagination within one SQL statement/snapshot. The response shape, workspace predicates, stable ordering, and page-size limit are preserved. No index or schema changes are needed.

Benchmark results measure local database query execution and response serialization size only. They exclude browser rendering, HTTP, Neon, serverless cold starts, concurrency, and real-user experience. Seven warm samples are diagnostic, not statistically robust tail latency. Production/browser performance targets remain unverified.

## Release boundary and next work

Initial implementation used isolated local databases only. No production key or credential is needed for local verification.

Release preparation on 2026-10-31: a fresh encrypted production backup passed an isolated restore rehearsal. A disposable PostgreSQL 17 database passed 12 concurrent same-request saves (exactly one transaction, receipt and tag), changed-payload rejection, and rollback after an injected tag-write failure. Production Neon HTTP checks ran in explicitly read-only transactions: Activity pagination/totals matched independent aggregates, and the creation statement passed EXPLAIN without executing it. This checks production schema/driver compatibility but does not claim a production write/concurrency test. No schema migration or financial data rewrite is part of this release.

For the web release: verify the deployed commit and compare financial records against the fresh encrypted baseline. Physical-device acceptance remains required before distributing a new native binary. Live Neon write/concurrency testing remains unperformed; PostgreSQL concurrency and Neon read-only compatibility have separate evidence above. Application rollback uses compatible code and retains all creation receipts and newer financial data; never restore an older snapshot over newer live activity merely to roll back code.

Next slices: persistent draft identity across reloads; audited/idempotent transfers; version checks and audit coverage for edit/delete/undo; recurring/import boundaries; independent recovery; then M2 reconciliation. M0 deployment inventory, real-user metrics, full currency/debt contracts, and physical-device baseline remain incomplete.
